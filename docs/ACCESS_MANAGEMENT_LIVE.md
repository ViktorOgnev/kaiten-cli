# Live-проверка управления доступами — 4 ноября 2026 года

Проверялась рабочая копия `kaiten-cli 0.3.5` с незакоммиченным расширением
управления доступами, базовый commit
`dfa601b53098c897cb4703824b2087e804e6d953`. Это целевая проверка новых команд,
а не новая полная live campaign всего CLI. Tenant class: пользовательская
тестовая компания. Использовался обычный API-токен явно выбранного профиля;
production-профиль не использовался. Сервер не изменялся.

## Исправление CLI и особенности контракта

- Создание карты без `sort_order` возвращало HTTP 500. С явной позицией оно
  прошло без дополнительной роли общего доступа. CLI теперь подставляет
  текущую Unix-метку времени при отсутствии позиции, как для документов;
  явно переданную позицию сохраняет. Исправление покрыто офлайн-регрессией
  и проверено реальным созданием с минимальными параметрами.
- Автор вложенного объекта может иметь только унаследованные права. До
  переноса в корень тест явно назначал ему прямую роль с `access_control`.
  Попытка оставить объект без управляющего возвращала HTTP 400. CLI сохраняет
  этот отказ и не выдаёт права автоматически.
- Пользовательские и групповые назначения возвращаются отдельно.
  `own_role_ids` / `role_ids` относятся к пользователю,
  `own_groups_role_ids` / `groups_role_ids` — к группам. Массивы могут быть
  `null`. `role_permissions` отражает итоговые разрешения.
- После удаления пространства или карты их обычный GET мог возвращать 403.
  Отсутствие активного объекта проверялось административным листингом;
  один 403 доказательством удаления не считался.

## Очистка и воспроизведение

Временные объекты имели уникальные имена. Cleanup регистрировался после
создания и выполнялся в `finally`; подтверждены удаление сущностей, группы,
роли и отсутствие выданных тестовых назначений. HTTP 500 на виртуальном
получателе не запускал повторную запись. Удаление виртуального пользователя
проверялось через список активных виртуальных пользователей.

Приватные manifest, cleanup queue и JSONL trace сохранялись вне репозитория.
Credentials, tenant URL и идентификаторы тестовых объектов в этот отчёт не
включены. Существующие определения ролей и административные разрешения
реальных пользователей не менялись.

```bash
KAITEN_LIVE=1 \
KAITEN_ACCESS_LIVE_PROFILE=<test-profile> \
KAITEN_ACCESS_LIVE_DOMAIN=<expected-profile-domain> \
  .venv/bin/pytest -q -s -m live tests/live/test_access_management_live.py
```

Домен профиля должен точно совпадать с явно заданной целью. Нужны модули
групп, документов и карт историй, соответствующие административные права и
второй существующий платный участник тестовой компании. Новые внешние
приглашения не отправляются. Проверка виртуального получателя использует
прямой POST API только для подготовки тестовых данных: команды создания
пользователя компании в CLI нет. Все проверяемые операции выполняются через CLI.

Для сохранения журнала после pytest можно задать `KAITEN_ACCESS_LIVE_DIR`
приватным временным каталогом. Повторный запуск запрещён, пока в нём есть
неразрешённые записи cleanup. Порядок обычных live-проверок описан в
[LIVE_VALIDATION.md](../LIVE_VALIDATION.md).
